Bro, lo pernah nggak sih ngerasain aplikasi lo jadi *laggy* padahal server udah kenceng? Atau pas nge-run query `SELECT` malah timeout? Nah, kemungkinan besar masalahnya ada di **database index**.

Index itu ibarat **daftar isi di buku**, lo bisa langsung loncat ke halaman yang lo mau tanpa harus baca satu-satu. Tanpa index, database harus **full table scan** alias ngecek semua row satu per satu. Bayangin lo buka kamus tapi harus baca dari halaman 1 terus sampai ketemu kata yang lo cari. Ribet kan?

Nah, di artikel ini gw bakal jelasin gimana cara optimize query database lu pakai index. Complete, from scratch, plus contoh kode yang bisa lo langsung prakticin!

## Kenapa Index Itu Penting?

Oke, gw kasih simulasi sederhana biar lu paham bedanya.

### Tanpa Index

```sql
SELECT * FROM users WHERE email = 'john@example.com';
```

Tanpa index, database-nya bakal kayak gini:

```
Scanning 1,000,000 rows...
Mulai dari row #1
Row #2... Row #3... Row #4...
...
Baru ketemu di row #847,293
```

Waktu: **3.2 detik** (untuk 1 juta row)

### Dengan Index

```sql
CREATE INDEX idx_users_email ON users(email);

SELECT * FROM users WHERE email = 'john@example.com';
```

Dengan index, database langsung loncat:

```
Index lookup: idx_users_email
Langsung ketemu di row #847,293
```

Waktu: **0.003 detik**

**Itungan kasarnya:** tanpa index query lo bisa 1000x lebih lambat. Bro, ini beneran ngaruh ke user experience aplikasi lu!

## Jenis-Jenis Index yang Perlu Lu Tau

### 1. B-Tree Index (yang paling umum)

Ini tipe index yang paling sering dipake di PostgreSQL, MySQL, dll. Cocok untuk data yang bisa di-sort dan di-range query.

```sql
-- Contoh: Index untuk kolom yang sering di-WHERE
CREATE INDEX idx_orders_status ON orders(status);

-- Compound index (index untuk multiple kolom)
CREATE INDEX idx_products_category_price ON products(category, price);
```

**Kapan dipake:**
- ✅ Kolom yang sering muncul di `WHERE`
- ✅ Kolom yang di-`ORDER BY`
- ✅ Range query (`BETWEEN`, `>`, `<`)

### 2. Hash Index

Cepat untuk **exact match** doang, tapi nggak bisa buat range query.

```sql
-- MySQL
ALTER TABLE users ADD INDEX email_idx (email) USING HASH;
```

**Kapan dipake:**
- ✅ Lookup exact value (`WHERE email = 'xxx'`)
- ❌ Nggak bisa `WHERE price > 50000`
- ❌ Nggak bisa `ORDER BY`

### 3. Full-Text Index

Buat search teks yang panjang, kayak fitur search di blog atau e-commerce.

```sql
-- MySQL Full-Text Index
ALTER TABLE articles ADD FULLTEXT INDEX ft_title_content (title, content);

-- Query search
SELECT * FROM articles
WHERE MATCH(title, content) AGAINST('optimasi database');
```

```sql
-- PostgreSQL Full-Text Search
CREATE INDEX ft_products_desc ON products USING GIN(to_tsvector('indonesian', description));

SELECT * FROM products
WHERE to_tsvector('indonesian', description) @@ to_tsquery('indonesian', 'database & optimasi');
```

### 4. Composite Index (Index Multi-Kolom)

Index yang covering lebih dari satu kolom. Super powerful kalo dipake dengan bener.

```sql
CREATE INDEX idx_sales_date_region ON sales(sale_date, region, amount);
```

**Attention:** Urutan kolom di composite index itu **matters**!

```sql
-- Ini bener: kolom pertama selalu di-WHERE
CREATE INDEX idx_orders ON orders(customer_id, order_date, status);

-- Query yang bakal optimal:
SELECT * FROM orders WHERE customer_id = 123;                    -- ✅ Index digunakan
SELECT * FROM orders WHERE customer_id = 123 AND order_date > '2024-01-01'; -- ✅ Index digunakan
SELECT * FROM orders WHERE order_date = '2024-01-01';           -- ❌ Index nggak digunakan!
```

> **Rule of thumb:** Kolom yang paling **selective** (banyak unique value) taruh di depan.

## Best Practice dalam Membuat Index

### ✅ Do's: Yang Sebaiknya Lu Lakuin

#### 1. Index kolom yang sering di-WHERE

```sql
-- Dashboard analytics sering di-query gini:
SELECT * FROM transactions
WHERE user_id = 123
AND transaction_date BETWEEN '2024-01-01' AND '2024-12-31'
AND status = 'completed';

-- Buat index yang cover semua kolom di WHERE
CREATE INDEX idx_transactions_lookup ON transactions(user_id, transaction_date, status);
```

#### 2. Index kolom foreign key

```sql
-- Tabel orders punya foreign key ke users
CREATE INDEX idx_orders_user_id ON orders(user_id);

-- Tabel order_items punya foreign key ke orders
CREATE INDEX idx_order_items_order_id ON order_items(order_id);
```

Ini penting banget buat evit **sequential scan** pas nge-join tabel.

#### 3. Index kolom yang di-ORDER BY

```sql
-- Query yang perlu di-sort by tanggal
SELECT * FROM blog_posts
WHERE published = true
ORDER BY published_at DESC;

-- Index yang optimal
CREATE INDEX idx_blog_posts_published_date ON blog_posts(published, published_at DESC);
```

#### 4. Pakai `INCLUDE` buat covering index (PostgreSQL)

Covering index = index yang juga nyimpen kolom lain, jadi query nggak perlu akses ke tabel utama.

```sql
-- Tanpa covering index, ada 2 step:
-- Step 1: Index scan
-- Step 2: Lookup ke tabel utama (expensive!)

-- Dengan covering index:
CREATE INDEX idx_orders_covering ON orders(customer_id) INCLUDE (order_date, total_amount, status);

-- Query ini jadi super fast, langsung dari index doang!
SELECT order_date, total_amount, status
FROM orders
WHERE customer_id = 123;
```

### ❌ Don'ts: Yang Harus Lu Hindari

#### 1. Jangan index kolom yang jarang di-query

```sql
-- ❌ Bad: Index yang nggak pernah dipake
CREATE INDEX idx_users_hobby ON users(hobby);  -- Hobby jarang di-WHERE kan?

-- ✅ Good: Index yang sering dipake
CREATE INDEX idx_users_email ON users(email);
```

#### 2. Jangan bikin terlalu banyak index

Bro, index itu **double-edged sword**. Di satu sisi bikin `SELECT` cepat, tapi di sisi lain:

- **Write performance drop**: Setiap `INSERT`, `UPDATE`, `DELETE` harus update index juga
- **Storage naik**: Index makan tempat di disk
- **Maintenance overhead**: Database harus maintain lebih banyak struktur

```sql
-- ❌ Too many indexes on write-heavy table
CREATE INDEX idx1 ON orders(created_at);
CREATE INDEX idx2 ON orders(updated_at);
CREATE INDEX idx3 ON orders(status);
CREATE INDEX idx4 ON orders(customer_id);
CREATE INDEX idx5 ON orders(payment_method);
-- etc...
```

**Kapan terlalu banyak?** Untuk tabel yang heavy write, **maksimal 3-4 index** aja. Untuk read-heavy (reporting, analytics), bisa lebih banyak.

#### 3. Jangan index kolom dengan cardinality rendah

```sql
-- ❌ Bad: Boolean field, cuma 2 nilai (true/false)
CREATE INDEX idx_products_is_active ON products(is_active);
-- Database bakal return 50% data, index nggak ngaruh

-- ✅ Good: High cardinality columns
CREATE INDEX idx_products_sku ON products(sku);
CREATE INDEX idx_products_category ON products(category_id);
```

## Studi Kasus: E-Commerce Database Optimization

Gw mau kasih contoh real-world. Kita punya tabel `orders` dengan **1 juta row**:

### Before Optimization

```sql
-- Query yang lambat
EXPLAIN ANALYZE
SELECT o.id, o.order_number, o.total_amount, o.created_at,
       u.name as customer_name, u.email as customer_email
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.status = 'completed'
AND o.created_at >= '2024-01-01'
ORDER BY o.created_at DESC
LIMIT 20;
```

Output (sebelum optimize):

```
Gather  (cost=1000.00..89523.45 rows=20 width=68)
  ->  Parallel Seq Scan on orders o  (cost=...)
        Filter: ((status = 'completed') AND (created_at >= '2024-01-01'))
        Rows Removed by Filter: 892,340
```

> **Sequential scan!** 892,340 rows di-remove. Ini mah lambat banget bro.

### After Optimization

```sql
-- Step 1: Buat composite index yang cover WHERE clause
CREATE INDEX idx_orders_status_created ON orders(status, created_at DESC);

-- Step 2: Index untuk JOIN
CREATE INDEX idx_orders_user_id ON orders(user_id);

-- Step 3: Analyze table buat update statistics
ANALYZE orders;
```

Jalankan query yang sama lagi:

```
Index Scan using idx_orders_status_created on orders o  (cost=...)
  Index Cond: ((status = 'completed') AND (created_at >= '2024-01-01'))
  ->  Index Scan using idx_users_pkey on users u
```

**Hasil:**
- Query time: **3.2 detik → 0.015 detik**
- Rows scanned: **892,340 → 847** (efisiensi 99.9%!)

## Tips & Trick Tambahan

### 1. Pakai `EXPLAIN ANALYZE` dulu

```sql
-- Sempre cek execution plan sebelum bikin index
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT * FROM orders WHERE customer_id = 123;
```

Ini nunjukin:
- Apakah index digunakan atau nggak
- Cost (semakin kecil semakin baik)
- Rows yang di-scan
- Actual time execution

### 2. Monitor index usage

```sql
-- PostgreSQL: Cek index yang jarang dipake
SELECT
    schemaname,
    tablename,
    indexname,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;
```

Index yang `idx_scan = 0` berarti **nggak pernah dipake**. Lu bisa DROP itu bro!

### 3. Pakai partial index kalo bisa

Partial index = index cuma untuk subset data. Lebih kecil dan lebih cepat.

```sql
-- ❌ Full index: semua data
CREATE INDEX idx_orders_all ON orders(created_at);

-- ✅ Partial index: cuma data 30 hari terakhir
CREATE INDEX idx_orders_recent ON orders(created_at)
WHERE created_at >= NOW() - INTERVAL '30 days';
```

### 4. Naming convention

```sql
-- ✅ Good: Clear dan descriptive
CREATE INDEX idx_orders_customer_id ON orders(customer_id);
CREATE INDEX idx_orders_status_created ON orders(status, created_at DESC);
CREATE INDEX fk_orders_users ON orders(user_id);

-- ❌ Bad: Ambiguous
CREATE INDEX idx1 ON orders(customer_id);
CREATE INDEX idx_order ON orders(id);
```

## Kesimpulan

Bro, index itu tools yang super powerful buat optimize database performance. Intinya:

| Do's | Don'ts |
|------|--------|
| Index kolom di WHERE clause | Jangan index kolom yang jarang dipake |
| Index foreign key | Jangan bikin 10+ index di tabel yang heavy write |
| Composite index dengan urutan yang bener | Jangan index kolom boolean / low cardinality |
| Pakai EXPLAIN ANALYZE dulu | Jangan asal bikin index tanpa planning |
| Monitor & cleanup unused index | Jangan lupa ANALYZE setelah bikin index |

Kunci utamanya: **lu harus ngerti pola query aplikasi lu**. Nggak semua kolom harus di-index, tapi kolom yang sering di-`WHERE`, `JOIN`, dan `ORDER BY` itu WAJIB ada index-nya.

Udah gitu aja sih. Sekarang giliran lu, buka terminal, jalankan `EXPLAIN ANALYZE` di query yang paling lambat, dan bikin index-nya!
