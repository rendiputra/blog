Lo bikin project Laravel yang keren. Ada fitur login dengan OAuth, payment gateway, dan API keys ke berbagai third-party services.

File `.env` lo isinya:

```bash

DB_PASSWORD=super_secret_password_123
STRIPE_API_KEY=sk_live_abc123xyz789
AWS_ACCESS_KEY_ID=AKIAIOSFODNN7EXAMPLE
AWS_SECRET_ACCESS_KEY=wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY
TWILIO_AUTH_TOKEN=abcdef123456789
JWT_SECRET=very_secret_jwt_key_do_not_share
PAYPAL_CLIENT_SECRET=EBjisefj2343242...
```

Dan karena "males ngetik ulang pas deploy", lo push ke GitHub:


## Kenapa Secrets di Source Code Itu Berbahaya?

Oke, pertama lo harus paham kenapa ini problem.

### Git Itu Permanent

```
Lo push secrets ke GitHub

      ▼
┌─────────────────────────────────────┐
│ GitHub Repository                   │
│ | Commits are permanent            │
│ | History can't be deleted easily   │
│ | Anyone with repo access can see  │
└─────────────────────────────────────┘

Lo hapus dari commit berikutnya

      ▼
┌─────────────────────────────────────┐
│ GitHub Repository                   │
│ | Secrets still exist in history   │
│ | git filter-branch = painful      │
│ | GitHub Advanced Security = baru  │
└─────────────────────────────────────┘

Lo think it's deleted? Think again.
```

Even kalo lo hapus dari commit terbaru, secrets masih ada di Git history. Dan siapa tau secrets lu udah ke-clone sama bot atau orang yang lihat sebelum lo hapus.

### GitHub Scanning Itu Realtime

```
Bot scanning GitHub public repos 24/7

Timeline:
| 00:00 | Commit dengan secrets pushed
| 00:01 | Bot finds secrets in commit
| 00:02 | Secrets posted to dark web marketplace
| 00:05 | Someone buys your Stripe key for $50
| 00:10 | Unauthorized charges appear on your account
| 01:00 | You get email: "Your Stripe key has been used"
```

GitHub Advanced Security scan secrets secara realtime. Tapi itu nggak berarti lo boleh lengah. Scanning itu defense-in-depth, bukan excuse buat careless.

### Secrets Rotation Nightmare

```bash
# Lo ganti semua secrets karena udah bocor

New secrets generated:
| STRIPE_API_KEY=sk_live_new_xyz123
| AWS_ACCESS_KEY=AKIA_new_key_example
| DB_PASSWORD=new_secure_password

But now you need to:
| 1. Update production server
| 2. Update staging server
| 3. Update development machines (all team members)
| 4. Update CI/CD pipelines
| 5. Update documentation
| 6. Hope you didn't miss anything

Time spent: 4 hours
Stress level: Maximum
```

Secrets yang bocor harus di-rotated. Dan kalo lo manage secrets dengan cara yang berantakan, rotation itu nightmare.

## Best Practice #1: .gitignore .env

Ini langkah paling basic yang harus lo lakuin sekarang juga.

### Buat .gitignore

```bash
# .gitignore

# Environment files (HARUS ADA!)
.env
.env.local
.env.*.local
.env.production
.env.staging

# Never commit these files
*.pem
*.key
credentials.json
secrets.json

# IDE files (optional but recommended)
.idea/
.vscode/
*.swp
*.swo

# OS files
.DS_Store
Thumbs.db
```

### Verify .gitignore Works

```bash
# Cek apakah .env ke-ignore
git check-ignore -v .env

# Output kalo ke-ignore:
# .env    .gitignore:1:.env

# Output kalo nggak ke-ignore:
# (nothing)
```

### Reset Git History (Kalo Udah Ke-push)

Ini perlu kalo secrets lu udah kepush sebelumnya:

```bash
# ⚠️ WARNING: Ini akan rewrite history
# Pastikan lo backup dulu

# Install git-filter-repo
pip install git-filter-repo

# Remove .env dari seluruh history
git filter-repo --path .env --invert-paths

# Force push ke remote
git push origin --force --all
git push origin --force --tags

# Notify team members to re-clone
```

** Atau bisa juga pake GitHub's "Remove sensitive data" tool:**

1. Buka repository di GitHub
2. Settings | Danger Zone | Remove sensitive data
3. Ikuti wizard untuk hapus file dari history

## Best Practice #2: Environment Variables di VPS

Sekarang lo udah exclude .env dari git. Tapi lo masih butuh cara buat nge-set secrets di server production.

### Method 1: Systemd Environment Variables

Ini cara paling aman untuk aplikasi yang jalan sebagai systemd service:

```bash
# Buat file environment untuk service
sudo nano /etc/systemd/system/myapp.service.d/override.conf
```

```ini
[Service]
Environment="NODE_ENV=production"
Environment="PORT=3000"
Environment="DATABASE_URL=postgresql://user:password@localhost:5432/dbname"
Environment="REDIS_URL=redis://localhost:6379"
Environment="STRIPE_API_KEY=sk_live_xxx"
Environment="JWT_SECRET=super_secure_jwt_secret_here"
```

```bash
# Reload systemd dan restart service
sudo systemctl daemon-reload
sudo systemctl restart myapp
sudo systemctl status myapp
```

**Kelebihan:** Secrets tersimpan di sistem, nggak visible di process list

**Kekurangan:** Satu file per service, nggak scalable

### Method 2: /etc/environment

Simpler tapi kurang secure:

```bash
# Edit /etc/environment
sudo nano /etc/environment

# Tambah baris:
APP_ENV=production
DATABASE_URL=postgresql://user:pass@localhost/db
REDIS_URL=redis://localhost:6379
```

```bash
# Reload
source /etc/environment

# Atau logout/login ulang
```

### Method 3: Bash Profile (Development Only)

**Nggak recomended untuk production.** Tapi useful untuk development:

```bash
# ~/.bashrc atau ~/.bash_profile
nano ~/.bashrc

# Tambah di akhir file:
export NODE_ENV=development
export DATABASE_URL=postgresql://localhost/mydb
export API_KEY=your_api_key_here

# Load
source ~/.bashrc
```

### Access Environment Variables di Code

```javascript
// Node.js
console.log(process.env.DATABASE_URL);
console.log(process.env.API_KEY);

// Laravel (PHP)
echo env('DATABASE_URL');
echo env('API_KEY');

// Python
import os
print(os.environ['DATABASE_URL'])

// Go
os.Getenv("DATABASE_URL")
```

## Best Practice #3: Doppler (Recommended)

Doppler itu secrets management platform yang bikin kerja dengan environment variables jadi sangat gampang.

**Kenapa Doppler?**
- Single source of truth buat semua secrets
- Auto-inject ke aplikasi
- Audit log buat semua access
- Team collaboration dengan RBAC
- Integrasi dengan semua platform

### Setup Doppler

**Step 1: Daftar dan Install**

```bash
# Install Doppler CLI
# macOS
brew install dopplerhq/cli/doppler

# Linux
curl -fsSL https://cli.doppler.com/install.sh | sudo bash

# Windows
scoop install doppler

# Login
doppler login

# Verify
doppler setup
```

**Step 2: Buat Project**

1. Buka [doppler.com](https://doppler.com)
2. Klik **New Project**
3. Beri nama: `my-awesome-app`
4. Pilih environment: Development, Staging, Production
5. Tambah secrets:

```bash
# Lewat CLI
doppler secrets set STRIPE_API_KEY=sk_live_xxx
doppler secrets set DATABASE_URL=postgresql://...
doppler secrets set JWT_SECRET=your_jwt_secret

# Atau import dari .env file
doppler secrets import --project my-app --env dev < .env.example
```

**Step 3: Setup di Server**

```bash
# Install Doppler di server
curl -fsSL https://cli.doppler.com/install.sh | sudo bash

# Setup dengan service token (recommended)
doppler setup --project my-app --config production

# Generate service token dari dashboard
# Settings | Service Tokens | Create Token

# Save token
sudo nano /etc/doppler.yaml
```

```yaml
# /etc/doppler.yaml
config: production

# Atau pakai environment variable
# DOPPLER_TOKEN=dp.st.prod.xxx
```

**Step 4: Run Aplikasi dengan Doppler**

```bash
# Without doppler (nggak recomended)
node app.js

# With doppler (recommended)
doppler run -- node app.js

# Dengan service token
DOPPLER_TOKEN=dp.st.prod.xxx doppler run -- node app.js

# Systemd service
sudo nano /etc/systemd/system/myapp.service
```

```ini
[Unit]
Description=My Awesome App
After=network.target

[Service]
ExecStart=/usr/local/bin/doppler run -- /usr/bin/node /var/www/myapp/app.js
Environment="DOPPLER_TOKEN=dp.st.prod.xxx"
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
```

### Doppler dengan Docker

```yaml
# docker-compose.yml
services:
  app:
    image: node:20-alpine
    working_dir: /app
    command: ["doppler", "run", "--", "node", "index.js"]
    environment:
      DOPPLER_TOKEN: ${DOPPLER_TOKEN}
    volumes:
      - ./src:/app
    depends_on:
      - db
      - redis

  db:
    image: postgres:15-alpine
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD}
```

```bash
# Run dengan token
DOPPLER_TOKEN=dp.st.prod.xxx docker-compose up
```

### Doppler dengan CI/CD

```yaml
# GitHub Actions (.github/workflows/deploy.yml)
name: Deploy

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Doppler
        uses: dopplerhq/setup@v1
        with:
          token: ${{ secrets.DOPPLER_TOKEN }}

      - name: Install dependencies
        run: npm ci

      - name: Run tests
        run: npm test

      - name: Deploy
        run: |
          doppler run -- npm run deploy
        env:
          DOPPLER_TOKEN: ${{ secrets.DOPPLER_TOKEN }}
```

## Best Practice #4: AWS Parameter Store

Kalo lo udah di ekosistem AWS, Parameter Store itu pilihan yang solid.

### Kenapa AWS Parameter Store?

```
Alternatives:
| AWS Secrets Manager | $0.40 per secret/month | Advanced features
| AWS Parameter Store | FREE (Standard tier) | Basic secrets
| HashiCorp Vault     | Self-hosted | Full control
| Doppler            | $3/user/month | Developer-friendly

Parameter Store: FREE, integrated AWS, good enough
```

### Setup Parameter Store

**Step 1: Create Parameters via Console atau CLI**

```bash
# Create String (unencrypted)
aws ssm put-parameter \
  --name "/my-app/production/DATABASE_URL" \
  --value "postgresql://user:pass@host:5432/db" \
  --type String

# Create SecureString (encrypted)
aws ssm put-parameter \
  --name "/my-app/production/STRIPE_API_KEY" \
  --value "sk_live_xxx" \
  --type SecureString

# Create dengan KMS encryption
aws ssm put-parameter \
  --name "/my-app/production/JWT_SECRET" \
  --value "super_secret" \
  --type SecureString \
  --key-id alias/aws/ssm
```

**Step 2: Set IAM Permissions**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "ssm:GetParameter",
        "ssm:GetParameters"
      ],
      "Resource": [
        "arn:aws:ssm:region:account:parameter/my-app/production/*"
      ]
    }
  ]
}
```

**Step 3: Access dari EC2/ECS**

```bash
# EC2 instance profile udah punya permissions
aws ssm get-parameter \
  --name "/my-app/production/STRIPE_API_KEY" \
  --with-decryption

# Get multiple parameters
aws ssm get-parameters \
  --names "/my-app/production/DATABASE_URL" "/my-app/production/STRIPE_API_KEY" \
  --with-decryption
```

**Step 4: Auto-load di Application**

```javascript
// Node.js AWS SDK v3
const { SSMClient, GetParametersCommand } = require('@aws-sdk/client-ssm');

const client = new SSMClient({ region: 'ap-southeast-1' });

async function loadSecrets() {
  const command = new GetParametersCommand({
    Names: [
      '/my-app/production/DATABASE_URL',
      '/my-app/production/STRIPE_API_KEY',
      '/my-app/production/JWT_SECRET'
    ],
    WithDecryption: true
  });

  const response = await client.send(command);

  const secrets = {};
  for (const param of response.Parameters) {
    const key = param.Name.split('/').pop(); // Ambil nama terakhir
    secrets[key] = param.Value;
  }

  return secrets;
}

async function main() {
  const secrets = await loadSecrets();

  process.env.DATABASE_URL = secrets.DATABASE_URL;
  process.env.STRIPE_API_KEY = secrets.STRIPE_API_KEY;
  process.env.JWT_SECRET = secrets.JWT_SECRET;

  // Start app
  app.listen(3000);
}
```

## Best Practice #5: HashiCorp Vault

Vault itu untuk lo yang butuh full-featured secrets management dengan self-hosted option.

```bash
# Install Vault
# https://developer.hashicorp.com/vault/install

# Start dev server (testing only!)
vault server -dev

# Set secrets
vault kv put secret/my-app/database url="postgresql://..."
vault kv put secret/my-app/stripe api_key="sk_live_xxx"

# Read secrets
vault kv get secret/my-app/database

# Enable AppRole auth untuk machines
vault auth enable approle

# Generate role
vault write auth/approle/role/my-app \
  token_ttl=1h \
  token_policies=my-app-policy
```

## Environment Variables Best Practices

Apapun tools yang lo pake, ada principles yang harus lo follow:

### 1. Never Log Secrets

```javascript
// ❌ BAD: Nggak pernah log environment variables
console.log('Connecting to DB:', process.env.DATABASE_URL);
console.log('API Key:', process.env.API_KEY);

// ✅ GOOD: Log dengan mask
console.log('Connecting to DB:', process.env.DATABASE_URL.replace(/:.*@/, ':****@'));

// ❌ BAD: Error message mengandung secrets
throw new Error(`Failed to connect with key ${process.env.API_KEY}`);
```

### 2. Fail Fast Kalo Secrets Missing

```javascript
// ✅ GOOD: Validate secrets di startup
const required = ['DATABASE_URL', 'API_KEY', 'JWT_SECRET'];

for (const key of required) {
  if (!process.env[key]) {
    throw new Error(`Missing required environment variable: ${key}`);
  }
}
```

### 3. Separate Environments

```
Development:
| DATABASE_URL=postgresql://localhost/dev_db
| DEBUG=true
| LOG_LEVEL=debug

Staging:
| DATABASE_URL=postgresql://staging-db.internal/staging_db
| DEBUG=false
| LOG_LEVEL=info

Production:
| DATABASE_URL=postgresql://prod-db.internal/prod_db
| DEBUG=false
| LOG_LEVEL=warning
```

### 4. Rotate Regularly

```
Rotation schedule:
| API Keys | Every 90 days atau immediately kalo bocor
| Database Passwords | Every 90 days
| JWT Secrets | Every 30 days
| AWS Keys | Every 90 days

Tools untuk auto-rotation:
| Doppler Secrets Rotation
| AWS Secrets Manager Auto-Rotation
| HashiCorp Vault
```

### 5. Audit Access

```
Lo harus tau:
| Siapa yang akses secrets?
| Kapan secrets di-read?
| Dari mana (IP address)?
| Apakah ada unauthorized access?

Tools audit:
| Doppler Audit Log
| AWS CloudTrail
| HashiCorp Vault Audit Device
```

## Kesimpulan

Lo udah belajar:

**Kenapa secrets di source code itu berbahaya:**
- Git itu permanent, history nggak bisa dihapus mudah
- GitHub scanning realtime tapi lo nggak boleh lengah
- Rotation jadi nightmare kalo manage sembarangan

**Best practices:**
- .gitignore .env file
- Environment variables di VPS (systemd, /etc/environment)
- Doppler buat centralized secrets management
- AWS Parameter Store untuk AWS ecosystem
- HashiCorp Vault untuk enterprise

**Security principles:**
- Never log secrets
- Fail fast kalo missing
- Separate environments
- Rotate regularly
- Audit access

**The takeaway:**

Secrets management itu bukan optional | itu mandatory. Lo harus treat secrets sama kayak uang | simpen di tempat yang aman, rotate secara berkala, dan monitor siapa yang akses.

Lo sekarang udah punya tools dan knowledge buat implement secrets management yang proper. Mulai dari hal yang simple dulu | setup .gitignore, terus migrate ke tools yang lebih advanced sesuai kebutuhan.

Jangan tunggu sampe bocor dulu baru action. Prevention is always better than cure.
